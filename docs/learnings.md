# Learnings

Notes from building ReadSync, mostly about how ElevenLabs behaves.

## Timing and alignment

- **Timestamps come per character, in two versions.** The response has `alignment`, which maps to the text as written, and `normalized_alignment`, which maps to the text as spoken (for example "£12" → "twelve pounds"). ReadSync uses `alignment`, so the highlight stays on the reader's own words even when the voice says more.
- **Emojis are silent but stay in the timings.** The voice skips them, while `alignment` keeps each one with zero duration, starting when the next word starts. Composite emojis like 👩‍💻 arrive split into their parts (👩, a zero-width joiner, 💻) but join back into the original text, so highlight offsets stay correct. Because a standalone emoji starts at the same moment as the next word, the highlight goes straight to that word and never rests on the emoji. Silence is a deliberate default: screen readers announce emoji names, but in a read-along "party popper" would mostly be noise. A "describe emojis" setting could cover texts where an emoji carries meaning.
- **Whitespace isn't a universal word boundary.** Splitting on spaces works for English, French or German, but treats a whole Japanese sentence as one word. `Intl.Segmenter` is the planned fix.

## Text normalization and pronunciation

- **Expand text on the ElevenLabs side, not before sending it.** Rewriting text in code or with an LLM first (the docs suggest both) would make the timings map to the rewritten text, so readers would see words they never pasted. Text normalization and pronunciation dictionaries keep the original text intact.
- **Normalization `auto` isn't always enough.** With the default `apply_text_normalization: "auto"`, "£3,500.75" was read as a bare number without "pounds". ReadSync sets it to `on`.
- **Normalization expands abbreviations, but not reliably.** With normalization on, "i.e." and "e.g." were sometimes spoken as "that is" and "for example" and sometimes read letter by letter, depending on the sentence and the generation. A pronunciation dictionary with alias rules makes the expansion a fixed rule instead of the model's call; the multilingual model supports alias rules but not phoneme rules.
- **Pronunciation dictionaries don't know about languages.** A rule is a plain string replacement applied to every request, so English rules would also fire in a Spanish text (`etc.` → "et cetera" instead of "etcétera"), and other languages' abbreviations (`z. B.`, `p. ex.`) aren't covered at all. The rules are therefore keyed by language, one dictionary each; once the reader has a language picker, each request will send the dictionary for its language. Per-language alias lists are locale data, so a future improvement is managing them in a localization platform such as Lokalise, where translators can review their own language's abbreviations.

## Long texts

- **Sentence detection mistakes abbreviations for sentence ends.** `Intl.Segmenter` handles "a.m.", "e.g." and Japanese 。 correctly, but splits after "Dr.". Very short "sentences" are therefore attached to the one that follows, and sentences are grouped into chunks of about 800 characters, so most remaining mistakes fall inside a chunk instead of on a boundary where the voice would reset.
- **Chunks need context to sound like one reading.** Each request is generated independently, so ElevenLabs accepts `previous_text` and `next_text` to keep the intonation continuous. ReadSync sends the neighbouring chunks. The context isn't charged: a 42-character request with 306 characters of context used 42 credits. I haven't compared the audio side by side with requests sent without context yet.
- **Generating one chunk ahead is enough.** While a chunk plays, the next one is generated; in testing, the switch between chunks had no gap and no loading state, because each chunk takes far longer to play than to generate. A small first chunk (one or two sentences) keeps the wait before playback short.
- **The native audio player can't represent a chunked text.** Its timeline only knows the current chunk, so ReadSync uses its own controls: play/pause, previous/next sentence and speed. "Previous sentence" restarts the current sentence if it has played for over 1.5 seconds, like a music player's back button.
- **A request is paid for the moment it's sent.** I measured it with the account's character counter: a request cut off after 0.25 seconds, before any audio came back, was still charged for every character (77 of 77). The counter only updates 30–45 seconds later, which makes it easy to conclude the opposite from a quick check. So cancelling doesn't save credits; not sending does. The server still drops the ElevenLabs call when the browser disconnects, which saves it waiting on and downloading audio nobody will hear, but the levers on cost are elsewhere: how far ahead to generate (one chunk, so stopping early wastes at most one), and never sending the same request twice.
- **Deduplicate requests instead of cancelling them.** React StrictMode mounts components twice in development, so the reader requested its first two chunks twice on every text, and the aborted duplicates were charged in full. The client now sends each distinct request once and shares the in-flight result: StrictMode's second mount reuses the first mount's requests, and reading the same text again replays from memory without any request. The cache keys on the chunk and its neighbouring text and holds the last 20 chunks, with failed requests dropped so "Try again" sends a new one.

## Demo mode

- **A recorded fixture makes the demo free and repeatable.** The real responses for one sample text (audio and word timings per chunk) are recorded once and replayed by the server, so the demo needs no API key and spends no credits, and behaves exactly like the live app. Recordings are keyed on each chunk together with its context, because the same sentence with different neighbours is a different request; the recording script splits the text with the same function as the browser so the keys match.
- **Free-plan audio comes with conditions.** ElevenLabs' free plan only allows non-commercial use, and publishing its audio requires "elevenlabs.io" or "11.ai" in the title, so the demo's README heading, the in-app notice and any demo video carry that attribution.

## API keys

- **Restricted API keys need every feature they touch.** A key scoped to Text to Speech fails as soon as a request references a pronunciation dictionary, so the key also needs the Pronunciation Dictionaries permission.
- **Upstream errors need a translation and a log line.** Every ElevenLabs failure used to reach readers as "Speech generation failed." and left nothing in the server log, so running out of credits would have looked like a bug. The server now tells readers when the credits are used up or ElevenLabs is busy (a 429, for example from too many requests at once), and logs the original error behind every message it sends. I haven't seen a real quota error yet, so recognising it (`quota_exceeded` in the error body) is based on the shape of the other errors I've seen.

## Audio in the browser

- **Audio arrives as base64 inside JSON.** That lets audio and timings travel in one response, at the cost of a ~33% larger payload and no playback until the whole clip has arrived. Chunking keeps each clip short; streaming with timestamps could shorten the first wait further.
- **`timeupdate` is too coarse for word sync.** It fires only a few times per second, so the client reads `currentTime` on every animation frame while audio plays.

## Accessibility

- **A highlight colour is not enough on its own.** The yellow highlight looks obvious, but measured against the off-white reading background it has a contrast ratio of only about 1.2:1, far below the 3:1 that WCAG asks for indicators like this. It works through hue alone, which fails readers with colour vision deficiency or low vision, and anyone on a washed-out screen. The active word is now also underlined, dark on yellow (about 13:1) in both themes, which still marks it in a fully greyscale view. In dark mode the yellow itself already stands out at about 13:1. A first attempt drew the line as an inset shadow, which curved with the highlight's rounded corners and, sitting on its bottom edge, blended into the dark background; a real text underline kept inside the highlight, with `text-decoration-skip-ink: none` so it runs straight through descenders, fixed both. Adjustable highlight styles and colour themes are the next step.
- **Hundreds of focusable words would make the page unusable by keyboard.** Making every word a Tab stop would force keyboard users through each one to reach anything after the text. Instead the text uses "roving" focus: only one word is in the Tab order at a time, the arrow keys, Home and End move focus between words, and Enter reads from there. Space pauses and resumes, as in media players; an earlier version used it to read from a word too, which left no way to pause without leaving the text. Tabbing in lands on the word being spoken, so keyboard users join the reading where it is. Focusing a word scrolls it into view, so the words get a scroll margin to keep them clear of the sticky player.
